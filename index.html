Bloque 1 · Conceptos básicos

Programa, proceso, servicio e hilo

Los cuatro conceptos sobre los que se construye todo el módulo. Si entiendes la analogía de la cocina, tienes medio tema hecho.

Teoría La cocina

Receta= programa: instrucciones guardadas en disco. No hace nada sola.
Cocinero= CPU (un núcleo): sigue los pasos uno a uno.
Ingredientes= datos de entrada del programa.
Cocinando= proceso: la receta en marcha, con su PID y su memoria.
La misma receta cocinada dos veces son dos procesos: dos ventanas del navegador tienen dos PID distintos.

Proceso en memoria

Un proceso es un programa en ejecución: el código más todo lo necesario para ejecutarlo. Tiene un PID, su propia memoria (código, datos, heap, pila), ficheros y sockets abiertos, registros de CPU y al menos un hilo.

El PCB: la ficha de cada proceso

El sistema operativo guarda la información de cada proceso en su PCB (Process Control Block). Al cambiar de proceso, guarda y carga estos datos:

CampoPara qué sirve
PID y PPIDquién es y quién lo creó
Estadonuevo, listo, ejecución, bloqueado, terminado
Contador de programasiguiente instrucción a ejecutar
Registros de CPUpara reanudarlo donde lo dejó
Memoriadónde están código, datos, heap y pila
Ficheros y socketsrecursos abiertos
Usuario y permisoscontexto de seguridad
Prioridaddatos para el planificador

PID, PPID y jerarquía

Todo proceso tiene un PID y guarda el PPID (el PID de su padre). Todos descienden del proceso 1 (systemd o init en Linux). Desde Java:

ProcessHandle yo = ProcessHandle.current();
System.out.println("Mi PID: " + yo.pid());
yo.parent().ifPresent(p ->
    System.out.println("Mi PPID: " + p.pid()));

Zombis y huérfanos

Zombi · ya terminóSu padre no ha recogido el código de salida con wait(). No usa CPU pero ocupa un PID. En ps sale con Z o <defunct>.
Huérfano · sigue vivoSu padre terminó antes. Lo adopta init/systemd (PID 1), que recogerá su salida.
Un proceso bloqueado para siempre esperando un dato que nunca llega no es un zombi: sigue vivo. Es un error de programación.

Servicios (demonios)

Un servicio es un proceso no interactivo que el sistema arranca y controla sin intervención del usuario: sin ventana, suele arrancar con el sistema y da servicio a otros (impresión, red, bases de datos, servidores web).

# Windows
Get-Service | Where-Object Status -eq Running
# Linux (systemd)
systemctl list-units --type=service
systemctl status ssh

Hilos

Un hilo es un flujo de ejecución dentro de un proceso. Los hilos de un proceso comparten memoria y recursos; cada uno tiene su propia pila y su contador de programa. Solo se ejecutan a la vez si hay varios núcleos.

ProcesoHilo
Memoriapropia y aisladacompartida
Crearcostosobarato
ComunicarIPC (tuberías, sockets)variables compartidas
Si fallacae él solocae todo el proceso

# Linux / WSL

Bloque 2 · Tipos de programación

Concurrente, paralela y distribuida

Tres formas de hacer varias cosas a la vez, según haya uno o varios núcleos, o varios ordenadores.

Teoría Un cocinero o dos

Concurrencia · 1 cocineroPica la ensalada, para a remover la sopa y vuelve a picar. Los dos platos avanzan, pero nunca en el mismo instante.
Paralelismo · 2 cocinerosCada uno hace un plato. Avanzan a la vez de verdad: hacen falta dos núcleos.
La concurrencia es organizar varias tareas; el paralelismo es tener más manos para hacerlas a la vez.
TérminoSignificado
Concurrenciavarias tareas en curso a la vez; con un núcleo, el SO las alterna cada pocos milisegundos (multiprogramación).
Paralelismovarias tareas ejecutándose en el mismo instante en núcleos distintos (multiprocesamiento).
Multitareacapacidad del SO de mantener varias tareas en curso, con uno o con varios núcleos.

Programación distribuida

Varios ordenadores independientes, conectados por red, colaboran como si fueran un solo sistema. No comparten memoria: se comunican con mensajes.

EjemploQué reparte
Clústercálculo entre nodos de un centro de datos
Cloud (AWS, Azure, GCP)servidores y almacenamiento bajo demanda
Microserviciosuna aplicación en muchos servicios pequeños
Supercomputadorsimulación, meteorología, IA
VentajasEscala añadiendo máquinas y tolera fallos: si cae un nodo, siguen los demás.
InconvenientesLa red falla y tarda; sincronizar es difícil y hay que proteger los datos que viajan.

CPU-bound o I/O-bound

Limitada por CPU (CPU-bound)Limitada por E/S (I/O-bound)
Pasa el tiempo…calculandoesperando: disco, red, teclado, pantalla
Ejemploscalcular la física de un juego, comprimir, cifrarleer el mando, descargar, consultar una BBDD, dibujar en la tarjeta gráfica
Más núcleos ayudan…sí, hasta llenar los núcleospoco: mientras una espera, otra puede usar la CPU
Mientras una tarea I/O-bound espera (por ejemplo, a que el jugador pulse un botón) está bloqueada, y el planificador le da la CPU a otra que esté lista.

Paralelismo trivial (embarrassingly parallel)

Un problema es de paralelismo trivial cuando se parte en trozos independientes: ningún trozo necesita el resultado de otro. Cuatro coladas en cuatro lavadoras, o aplicar un filtro a cada foto de una carpeta. No lo es calcular Fibonacci o seguir los pasos de una receta en orden: cada paso depende del anterior.

4 coladas (30 min lavar + 45 min secar)TiempoTipo
Una lavadora y una secadora, carga a carga300 minsecuencial
Lavas la siguiente mientras se seca la anterior210 minconcurrente
Cuatro lavadoras y cuatro secadoras75 minparalela

Ley de Amdahl: el límite de añadir núcleos

Si solo una parte p del programa se puede paralelizar, la parte secuencial (1 − p) pone un techo. Con n núcleos, la aceleración es:

S = 1 / ((1 − p) + p / n)
Calculadora de Amdahl
Con un 80 % paralelizable, aunque tengas infinitos núcleos nunca pasas de 5×: el 20 % secuencial sigue tardando lo mismo.

Bloque 3 · Estados de un proceso

Cinco estados y seis transiciones

El ciclo de vida de un proceso, desde que se crea hasta que termina, y quién decide cada cambio.

Teoría El diagrama

  • Solo hay un proceso en ejecución por núcleo.
  • Los listos esperan CPU; los bloqueados esperan un suceso (disco, red, teclado).
  • Un bloqueado nunca pasa directo a ejecución: vuelve a Listo y espera turno.
  • Solo se bloquea quien se está ejecutando (Listo → Bloqueado es imposible).
  • Un terminado no revive: habría que crear otro proceso.

Bloque 4 · Planificación de la CPU

Quién usa cada núcleo, y cuándo

El planificador decide qué proceso pasa a ejecución. Aquí está la parte de cálculo del tema: diagramas de Gantt, tiempos de espera y de retorno.

Teoría Planificadores y políticas

A largo plazoDecide qué procesos nuevos entran en la cola de listos. Se ejecuta poco; casi no existe en ordenadores personales.
A corto plazoElige qué proceso de la cola de listos pasa a ejecución. Actúa cada pocos milisegundos: debe ser muy rápido.
PolíticaCuándo cambia de proceso
Cooperativasolo si el proceso se bloquea o termina (sin expropiación)
Apropiativaexpulsa al proceso si llega uno más prioritario
Tiempo compartidocada proceso tiene un quantum; al agotarlo, cede la CPU

Algoritmos

AlgoritmoCómo eligeRiesgo
FCFS (FIFO)por orden de llegadalos cortos esperan detrás de los largos
SJFel que necesita menos CPUinanición de los largos
Prioridadesel de mayor prioridadinanición de los de baja prioridad
Round Robinturnos de un quantum, en círculoquantum mal elegido
Colas multinivelvarias colas con distinto algoritmocomplejidad
Inanición: un proceso listo que nunca llega a ejecutarse. Se evita con envejecimiento (aging): la prioridad sube con el tiempo de espera.

Fórmulas que tienes que saber

Retornofin − llegada
Esperaretorno − ráfaga
Mediasuma ÷ nº de procesos

En Round Robin con llegadas, el orden de la cola manda: un proceso que llega durante un quantum se pone en la cola antes que el proceso que acaba de agotar su quantum.

El cambio de contexto

Al cambiar de proceso, el SO guarda el estado del saliente en su PCB y restaura el del entrante. Es tiempo en que la CPU no hace trabajo útil: por eso un quantum demasiado pequeño es mala idea.

Bloque 5 · Procesos en Java

ProcessBuilder configura, Process controla

Lo que haces en la terminal con java HolaMundo, ahora lo hará tu programa. Todo con JDK 21 o superior.

Teoría Las dos clases

ProcessBuilderConfigura el proceso antes de lanzarlo: command(), directory(), environment(), redirecciones. Lo lanza con start().
ProcessEl proceso hijo ya en marcha: pid(), waitFor(), exitValue(), destroy(), flujos de entrada y salida.
Ojo: start() es de ProcessBuilder, no de Process. Runtime.exec(String) está obsoleto desde Java 18. Si el ejecutable no existe o no tiene permisos, start() lanza IOException.

Lanzar y esperar

ProcessBuilder pb = new ProcessBuilder("ping", "-c", "3", "8.8.8.8"); // Windows: "-n"
pb.directory(new File(System.getProperty("user.home"))); // carpeta de trabajo
pb.environment().put("MODO", "prueba");  // variable de entorno
pb.inheritIO();                           // el hijo escribe en nuestra consola
Process p = pb.start();                   // puede lanzar IOException
System.out.println("PID del hijo: " + p.pid());
int codigo = p.waitFor();                // bloquea hasta que termina (0 = bien)
Excepción / reglaQué significa
IOExceptionstart() no pudo crear el proceso: no existe o sin permisos
InterruptedExceptionalguien interrumpió al padre mientras esperaba en waitFor(). Restablece con Thread.currentThread().interrupt()
Comando troceadoel programa y cada argumento por separado. Nunca "ping -c 3 8.8.8.8" en una sola cadena

Padre e hijo: argumentos de ida, código de salida de vuelta

El padre pasa datos al hijo como argumentos (llegan como texto en args, hay que convertirlos). El hijo responde con System.exit(n), y el padre recibe n como valor de waitFor().

Abrir una web según el sistema

SistemaComando para ProcessBuilder
macOS"open", url
Linux"xdg-open", url
Windows"cmd", "/c", "start", "", url

En Windows, start es una orden interna de cmd. El "" vacío es el título de la ventana: sin él, start toma la URL como título. El navegador que se abre no es hijo nuestro: nuestro hijo es open/cmd, que termina enseguida con código 0.

Bloque 6 · Comunicar y controlar

Hablar con el hijo, esperarlo y terminarlo

Leer lo que escribe el hijo, enviarle datos, encadenar procesos, observarlos y matarlos.

Teoría Tres flujos vistos desde el padre

Flujo del hijoEl padre lo usa conDirección
stdin (entrada)getOutputStream() / outputWriter()padre → hijo
stdout (salida)getInputStream() / inputReader()hijo → padre
stderr (errores)getErrorStream() / errorReader()hijo → padre
Truco para el examen: getInputStream() lee la salida del hijo. Los nombres están desde el punto de vista del padre: lo que para el padre es una entrada, para el hijo es su salida.

Por defecto los flujos van a tuberías (PIPE). Si el padre no las lee y el hijo escribe mucho, el búfer se llena y el hijo se bloquea. Por eso: lee primero, waitFor() después.

Leer la salida línea a línea

ProcessBuilder pb = new ProcessBuilder("java", "-version");
pb.redirectErrorStream(true);   // stderr se mezcla con stdout
Process p = pb.start();
try (BufferedReader br = p.inputReader(StandardCharsets.UTF_8)) {
    String linea;
    while ((linea = br.readLine()) != null) {  // null = el hijo cerró
        System.out.println("[hijo] " + linea);
    }
}
System.out.println("Código: " + p.waitFor());  // DESPUÉS de leer

java -version escribe en stderr: sin redirectErrorStream(true) no leerías nada por getInputStream().

Redirigir en lugar de leer

MétodoEfecto
inheritIO()los tres flujos a la consola del padre
redirectOutput(File)la salida a un fichero (lo sobrescribe)
Redirect.appendTo(f)la salida al final de un fichero
redirectInput(File)la entrada se lee de un fichero
redirectError(...)los errores a otro destino
Redirect.DISCARDdescarta la salida (Java 9+)

Enviar datos al hijo

Process p = new ProcessBuilder("sort").start();
try (BufferedWriter w = p.outputWriter()) {
    w.write("pera\nmanzana\nkiwi\n");
}   // cerrar = fin de datos para el hijo
System.out.print(new String(p.getInputStream().readAllBytes()));

Hay que cerrar el flujo: si no, el hijo sigue esperando datos y no termina nunca.

Esperar con límite y terminar

MétodoQué hace

destroyForcibly()lo mata sin avisar (SIGKILL)
exitValue()código de salida; excepción si aún no terminó
onExit()CompletableFuture que se completa al terminar

ProcessHandle: el Administrador de tareas desde Java

ProcessHandle.allProcesses()
    .filter(ph -> ph.info().command().isPresent())
    .limit(10)
    .forEach(ph -> System.out.println(ph.pid() + " " + ph.info().command().get()));

info() da orden, argumentos, usuario, hora de inicio y tiempo de CPU. children() y descendants() recorren el árbol (Java 9+).

Encadenar procesos: startPipeline

// Equivale a: ps -e | grep java | wc -l
List<Process> tuberia = ProcessBuilder.startPipeline(List.of(
    new ProcessBuilder("ps", "-e"),
    new ProcessBuilder("grep", "java"),
    new ProcessBuilder("wc", "-l")));
Process ultimo = tuberia.get(tuberia.size() - 1);

La salida de cada proceso se conecta a la entrada del siguiente sin pasar por Java y sin usar la shell.

Varios hijos a la vez y contar los vivos

Si lanzas los hijos con start() y no llamas a waitFor() en el mismo bucle, se ejecutan a la vez. Desde el padre, ProcessHandle.current().children() devuelve sus hijos directos.

// PadreHijos.java · lanza 3 hijos InfoHijo sin esperar
List<Process> lista = new ArrayList<>();
String cp = System.getProperty("java.class.path");  // el hijo busca InfoHijo.class donde el padre
for (int i = 1; i <= 3; i++) {
    ProcessBuilder pb = new ProcessBuilder("java", "-cp", cp, "InfoHijo", String.valueOf(i));
    lista.add(pb.inheritIO().start());           // sin waitFor() aquí
}
Thread.sleep(500);
long vivos = ProcessHandle.current().children().filter(ProcessHandle::isAlive).count();
System.out.println("Hijos vivos a los 0.5 s: " + vivos);   // 3: duermen 1 s
for (Process p : lista) p.waitFor();          // ahora sí, esperar a todos

// InfoHijo.java
long pid = ProcessHandle.current().pid();
long padre = ProcessHandle.current().parent().map(ProcessHandle::pid).orElse(0L);
System.out.println("Hijo " + args[0] + ": mi PID es " + pid + ", mi padre es " + padre);
Thread.sleep(1000);
Si pones waitFor() dentro del primer bucle, cada hijo espera al anterior y vuelves a lo secuencial. Es la misma trampa que con join() en los hilos del Tema 2.

Tema 2 · Bloque 1 · Proceso frente a hilo

El proceso es la cocina; los hilos, los cocineros

Un proceso es el contenedor de recursos. Un hilo es quien ejecuta las instrucciones. Todo proceso tiene al menos uno: en Java, el que ejecuta main.

Teoría Una línea de ejecución dentro de un proceso

Proceso = la cocinaNevera, fogones y despensa: memoria, ficheros y conexiones.
Hilos = cocinerosVarios trabajando en la misma cocina a la vez.
Libreta de cada cocineroPor dónde va: su pila y su contador de programa.

Desde el hilo principal podemos crear más hilos que avancen a la vez. Cada hilo puede ir en un núcleo distinto; con un solo núcleo, se turnan. Hay hilos del sistema (teclado, red, pantalla…) y hilos de usuario, los que creamos nosotros.

Qué comparten los hilos y qué no

Compartido por todos los hilos del proceso (la JVM)Propio de cada hilo
Heap (los objetos), variables static, ficheros abiertos, conexiones de redPila (variables locales) y contador de programa
Si dos hilos tienen la referencia a un objeto, ven el mismo. Compartir es rápido, pero peligroso si dos hilos escriben a la vez (lo veréis el 4 de noviembre: condiciones de carrera).

Para qué queremos hilos

Que no se congeleLa interfaz responde mientras otro hilo descarga, guarda o calcula.
Atender a muchosUn servidor dedica un hilo a cada cliente y no hace esperar a nadie.
Usar todos los núcleosUn cálculo grande se reparte en trozos, uno por núcleo.

Casi nunca se ve a simple vista: Future, callbacks, async/await y corrutinas funcionan siempre sobre hilos.

CPU-bound o IO-bound: cuántos hilos

CPU-boundIO-bound
Pasa el tiempo…calculandoesperando (red, disco, usuario)
Ejemploscomprimir, cifrar, renderizardescargar, consultar una BBDD
Los hilos ganan…solo si hay núcleos librescasi siempre: uno espera, otro trabaja
Cuántos hilos≈ núcleos disponiblesmuchos más que núcleos
int nucleos = Runtime.getRuntime().availableProcessors(); // cuántos núcleos ve la JVM
Regla del ejercicio 1: compartir datos pide hilo; aislar (que un fallo no tumbe al resto) pide proceso.

Tema 2 · Bloque 2 · Crear hilos en Java

Thread, Runnable y start()

La clase Thread y la interfaz Runnable son del paquete java.lang: no hay que importar nada.

Teoría Tres formas de decir qué hace un hilo

// 1. Heredar de Thread
class Cocinero extends Thread {
    public void run() { System.out.println("Cocino"); }
}
new Cocinero().start();

// 2. Implementar Runnable
class Pinche implements Runnable {
    public void run() { System.out.println("Pico cebolla"); }
}
new Thread(new Pinche()).start();

// 3. Lambda: Runnable tiene un solo método
new Thread(() -> System.out.println("Friego")).start();
Usa Runnable o lambdaSeparas la tarea del hilo que la ejecuta, y tu clase puede heredar de otra.
Heredar de ThreadFunciona, pero gastas la única herencia que permite Java.

En las tres, el trabajo va en run() y el hilo arranca con start().

HolaHilos: crear, arrancar y esperar

Runnable saludo = () -> System.out.println(
        "Hola desde " + Thread.currentThread().getName());
Thread t1 = new Thread(saludo, "T1");   // tarea + nombre
Thread t2 = new Thread(saludo, "T2");
t1.start(); t2.start();                 // arrancan a la vez
t1.join();  t2.join();                  // main espera a ambos
System.out.println("Fin del main");

$ java HolaHilos
Hola desde T2
Hola desde T1
Fin del main
  • Thread.currentThread() devuelve el hilo que está ejecutando esa línea.
  • El orden de T1 y T2 cambia entre ejecuciones: lo decide el planificador.
  • Sin los join(), «Fin del main» podría salir antes que los saludos.

El error clásico: llamar a run() en vez de start()

Thread t = new Thread(() -> {
    System.out.println("Me ejecuta: " + Thread.currentThread().getName());
}, "Worker");
t.run();    // NO crea hilo: lo ejecuta main → "Me ejecuta: main"
t.start();  // SÍ crea un hilo nuevo     → "Me ejecuta: Worker"
run()Lo que hace el hilo. Nunca lo llames tú.
start()Pide al sistema un hilo nuevo, y él llama a run(). Solo una vez: la segunda lanza IllegalThreadStateException.

Muchos hilos: un bucle para arrancar, otro para esperar

List<Thread> hilos = new ArrayList<>();
for (int i = 0; i < 8; i++) {
    int n = i;  // la lambda necesita una variable que no cambie
    Thread t = new Thread(() -> System.out.println("Hola desde H" + n), "H" + n);
    hilos.add(t);
    t.start();
}
for (Thread t : hilos) t.join();   // esperar a todos, después
Trampa: si haces join() dentro del primer bucle, cada hilo espera al anterior y vuelves a lo secuencial. Y dentro de la lambda no puedes usar i (cambia en cada vuelta): por eso se copia en n.

Tema 2 · Bloque 3 · Ciclo de vida de un hilo

Seis estados en Thread.State

Cada hilo pasa por ellos según lo que hacemos nosotros y lo que decide el sistema. Ojo: no son los mismos cinco estados de los procesos del Tema 1.

Teoría El diagrama

Qué provoca cada cambio de estado

Lo que ocurreEstado del hilo
new Thread(tarea)NEW
t.start()RUNNABLE
Thread.sleep(500)TIMED_WAITING
otro.join()WAITING
otro.join(2000)TIMED_WAITING
Entrar en un synchronized ocupadoBLOCKED
Esperar el teclado o la redRUNNABLE (¡ojo!)
Acaba run() o lanza una excepciónTERMINATED
stop() ya no existe: desde JDK 20 lanza UnsupportedOperationException. Para pedir a un hilo que pare: interrupt(). Consulta el estado con t.getState() o t.isAlive() (true si ya arrancó y no ha terminado).

Ver los estados con getState()

Thread t = new Thread(() -> {
    try { Thread.sleep(500); } catch (InterruptedException e) { }
});
System.out.println("1: " + t.getState());  // NEW
t.start();
System.out.println("2: " + t.getState());  // RUNNABLE
Thread.sleep(100);                          // damos tiempo a que se duerma
System.out.println("3: " + t.getState());  // TIMED_WAITING
t.join();
System.out.println("4: " + t.getState());  // TERMINATED

getState() es una foto: cuando la lees, el hilo ya puede haber cambiado. Úsalo para aprender y depurar, no para decidir qué hace el programa.

Tema 2 · Bloque 4 · Controlar hilos

join, sleep, interrupt y demonios

Esperar a que acabe, dormirlo, pedirle que pare y decidir si la JVM debe esperarlo al salir.

Teoría sleep y join: dormir y esperar

MétodoQué hace
Thread.sleep(ms)Duerme al hilo que lo llama, sin gastar CPU. Es static: no duermes a otro hilo, solo a ti mismo.
t.join()El hilo que llama espera hasta que t termine. Si ya terminó, vuelve al instante.
t.join(ms)Espera como mucho ese tiempo y sigue. Después comprueba con t.isAlive() si terminó.

Los tres pueden lanzar InterruptedException: es la forma en que Java avisa de que alguien ha pedido a ese hilo que pare.

interrupt(): pedir a un hilo que pare

Thread reloj = new Thread(() -> {
    int s = 0;
    try {
        while (true) {
            System.out.println("Tic " + s++);
            Thread.sleep(1000);
        }
    } catch (InterruptedException e) {
        System.out.println("Me han interrumpido: paro");
    }
});
reloj.start();
Thread.sleep(3500);
reloj.interrupt();   // pide parar, no mata
reloj.join();
  • interrupt() pone una marca en el hilo. Si está en sleep, join o wait, salta InterruptedException.
  • Si está calculando, debe mirar la marca él mismo con isInterrupted().
  • Es cooperativo: el hilo decide cómo y cuándo parar, y puede dejarlo todo ordenado.

Hilos demonio: la JVM no los espera

Thread guardado = new Thread(() -> {
    while (true) {
        System.out.println("Autoguardado...");
        try { Thread.sleep(300); } catch (InterruptedException e) { return; }
    }
});
guardado.setDaemon(true);   // siempre antes de start()
guardado.start();
Thread.sleep(1000);
System.out.println("Fin del main");  // y el programa acaba

La JVM termina cuando acaban todos los hilos normales; a los demonios los corta sin esperar. Sirven para tareas de fondo: autoguardado, limpieza, el recolector de basura. Sin setDaemon(true), este programa no terminaría nunca.

Millones de hilos esperando a la vez

Hilos ligeros que gestiona la JVM. No hacen el cálculo más rápido: hacen la espera más barata.

Teoría De plataforma frente a virtual

De plataformaVirtual
Lo gestionael sistema operativola JVM
Pila≈ 1 MB reservadounos KB, crece si hace falta
Cuántos cabenmilesmillones

Muchos hilos virtuales se reparten unos pocos hilos reales, los portadores. Como los camareros: no esperan junto a la mesa mientras el cliente decide; atienden otra y vuelven.

Crear un hilo virtual: igual que siempre

Runnable tarea = () -> System.out.println(Thread.currentThread());
Thread v = Thread.ofVirtual().name("virtual-1").start(tarea);
Thread p = Thread.ofPlatform().name("plataforma-1").start(tarea);
v.join(); p.join();
System.out.println("¿v es virtual? " + v.isVirtual());
// Atajo: Thread.startVirtualThread(tarea);

VirtualThread[#18,virtual-1]/runnable@ForkJoinPool-1-worker-1
Thread[#20,plataforma-1,5,main]
¿v es virtual? true

Es un Thread normal: join, sleep, interrupt y getState funcionan igual. La salida muestra el portador que lo ejecuta (ForkJoinPool-1-worker-1).

10.000 tareas que esperan 1 segundo ≈ 1,1 s

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        exec.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));  // simula la red
            return null;
        });
    }
}   // al cerrar el try, espera a que acaben todas

El ejecutor lanza un hilo virtual por cada tarea que le das con submit. Con try-with-resources no hacen falta join: el cierre espera por ti.

Ejercicio 5 · 100 hilos de plataforma contra virtuales

100 de plataforma · ≈ 10 s1000 tareas ÷ 100 hilos = 10 tandas de 1 segundo.
Virtuales · ≈ 1 sUn hilo por tarea: las 1000 esperan a la vez.
Si la tarea calcula en vez de dormir, los virtuales ya no ganan: los núcleos son los mismos y no hay esperas que aprovechar.

Gestor de descargas: cinco descargas, cuatro versiones

El mismo programa cuatro veces. Pulsa cada paso y mira cómo el total pasa de la suma a lo que tarda la más lenta.

Simulador Mira cada versión

Teoría El código de cada paso

static final String[] FICHEROS = {"foto.jpg", "video.mp4", "musica.mp3", "juego.zip", "apuntes.pdf"};
static final int[] SEGUNDOS = {1, 4, 2, 2, 1};

// Simula una descarga: tarda 'seg' segundos y dice qué hilo la hace
static void descargar(String nombre, int seg) {
    String hilo = Thread.currentThread().getName();
    System.out.printf("[%s] empieza %s%n", hilo, nombre);
    try {
        Thread.sleep(seg * 1000L);
        System.out.printf("[%s] terminado %s (%d s)%n", hilo, nombre, seg);
    } catch (InterruptedException e) {
        System.out.printf("[%s] CANCELADO %s%n", hilo, nombre);  // paso 4
    }
}
Paso 1 · Secuencial (10,0 s) 
static void secuencial() {
    for (int i = 0; i < FICHEROS.length; i++) descargar(FICHEROS[i], SEGUNDOS[i]);
}
Paso 2 · Un hilo por descarga (4,0 s) 
static void conHilos() throws InterruptedException {
    List<Thread> hilos = new ArrayList<>();
    for (int i = 0; i < FICHEROS.length; i++) {
        int n = i;
        Thread t = new Thread(() -> descargar(FICHEROS[n], SEGUNDOS[n]), "D-" + n);
        hilos.add(t);
        t.start();
    }
    for (Thread t : hilos) t.join();
}
Paso 3 · Hilos virtuales (4,0 s) 
static void conVirtuales() throws InterruptedException {
    List<Thread> hilos = new ArrayList<>();
    for (int i = 0; i < FICHEROS.length; i++) {
        int n = i;
        Thread t = Thread.ofVirtual().name("V-" + n)   // lo único que cambia
                .start(() -> descargar(FICHEROS[n], SEGUNDOS[n]));
        hilos.add(t);
    }
    for (Thread t : hilos) t.join();
}

Con 5 descargas no se nota. Con 100.000, solo la versión virtual aguanta.

Paso 4 · Cancelar lo que pase de 3 s (3,0 s) 
long limite = System.currentTimeMillis() + 3000;
for (Thread t : hilos) {
    long queda = limite - System.currentTimeMillis();
    if (queda > 0) t.join(queda);    // espera como mucho lo que queda
    if (t.isAlive()) t.interrupt();  // se pasó: cancelar
}
for (Thread t : hilos) t.join();      // que los cancelados acaben

Un solo límite para todas: cada join espera solo lo que queda. Ojo: join(0) espera para siempre. Por eso el if.

Adelanto Próxima sesión (4 nov): condiciones de carrera

static int cuenta = 0;   // compartida: está en el heap
Thread[] hilos = new Thread[4];
for (int i = 0; i < 4; i++) {
    hilos[i] = new Thread(() -> { for (int j = 0; j < 100_000; j++) cuenta++; });
    hilos[i].start();
}
for (Thread h : hilos) h.join();
System.out.println("Esperado 400000, obtenido " + cuenta);  // p. ej. 300110, y cada vez otro
cuenta++ no es una sola operación: lee, suma y escribe. Si dos hilos leen el mismo valor a la vez, uno de los dos incrementos se pierde. Se arregla con sección crítica, synchronized, clases atómicas y Lock.

Resumen Lo que tienes que llevarte

HiloLínea de ejecución dentro de un proceso. Comparte el heap; la pila es suya.
CrearRunnable o lambda + start(). Nunca llames a run() tú.
EstadosNEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
Esperarjoin() espera a otro hilo; join(ms) con límite; sleep(ms) te duerme a ti.
Pararinterrupt() pide parar. No te tragues la InterruptedException.
VirtualesPara muchas tareas que esperan. Para calcular, tantos hilos como núcleos.
